# Scenario 1 — SSH Authentication Monitoring

---

# Objective

Validate that Wazuh detects authentication activity generated by the OpenSSH service.

This scenario simulates both failed and successful SSH authentications.

---

# Background

SSH is one of the most frequently targeted services on Linux servers.

Attackers commonly attempt to:

- Password guessing
- Brute-force attacks
- Credential stuffing
- Unauthorized remote access

Monitoring SSH logs is therefore essential for every Security Operations Center.

---

# Environment Preparation

Initially, the Ubuntu endpoint did not contain the SSH server.

When checking the service:

```bash
sudo systemctl status ssh
```

the system returned:

```text
Unit ssh.service could not be found.
```

This indicated that OpenSSH Server was not installed.

---

# Installation

Install OpenSSH Server.

```bash
sudo apt install openssh-server -y
```

Enable and start the service.

```bash
sudo systemctl enable --now ssh
```

Verify service status.

```bash
sudo systemctl status ssh
```

Verify listening port.

```bash
sudo ss -tulpn | grep :22
```

Expected result:

```text
LISTEN ... :22
```

---

# Wazuh Configuration

Authentication monitoring was enabled inside **ossec.conf**.

```xml
<localfile>
    <log_format>syslog</log_format>
    <location>/var/log/auth.log</location>
</localfile>
```

Restart the agent.

```bash
sudo systemctl restart wazuh-agent
```

Verification:

```text
Analyzing file:
/var/log/auth.log
```

The endpoint was now forwarding authentication events to the Wazuh Manager.

---

# Attack Simulation

Generate failed authentications.

```bash
ssh soc_test@192.168.56.101
```

Several incorrect passwords were intentionally entered.

---

Generate a successful authentication.

```bash
ssh soc_test@192.168.56.101
```

After entering the correct password:

```text
Accepted password for soc_test from 192.168.56.1
```

---

Failed authentication generated:

|-------|-------------|
| 5503 | PAM Login Failure |
| 5760 | SSH Authentication Failure |

Successful authentication generated:

| Rule | Description |
|-------|-------------|
| 5715 | Successful SSH Login |

---

# MITRE ATT&CK

| Technique | Description |
|------------|-------------|
| T1110.001 | Password Guessing |
| T1021 | Remote Services |
| T1078 | Valid Accounts |

---

# SOC Investigation

The analyst observes multiple failed authentication attempts followed by a successful login.

Typical investigation questions include:

- Was the login expected?
- Is the source IP trusted?
- Did the account authenticate outside business hours?
- Were privileged commands executed afterward?
- Was the same IP involved in other alerts?

No malicious behavior beyond the simulated activity was observed.

---

# Security Impact

Without monitoring, repeated authentication failures may indicate:

- Password guessing
- Credential attacks
- Initial compromise attempts

Successful authentication after repeated failures may indicate that an attacker has obtained valid credentials.

---

# Recommendations

- Enforce strong password policies.
- Enable SSH key authentication.
- Disable root login.
- Limit authentication attempts.
- Deploy Fail2Ban or equivalent protection.
- Monitor all SSH authentication events.
- Correlate authentication events with privileged activity.

# Scenario 2 — File Integrity Monitoring (FIM)

---

# Objective

Validate Wazuh Syscheck by detecting unauthorized file modifications inside a protected directory.

---

# Background

Attackers frequently modify existing files after compromising a system.

Examples include:

- Web shells
- Configuration files
- Startup scripts
- Cron jobs
- Application code

File Integrity Monitoring allows security analysts to detect these changes immediately.

---

# Environment Preparation

A dedicated directory was created.

```bash
sudo mkdir -p /var/www/sensitive
```

A monitored file was created.

```bash
sudo nano /var/www/sensitive/config.php
```

Example content:

```text
MODIFICATION_DE_TEST_WAZUH=true
```

---

# Wazuh Configuration

Syscheck configuration.

```xml
<directories realtime="yes" report_changes="yes">
/var/www/sensitive
</directories>
```

Restart the Wazuh Agent.

```bash
sudo systemctl restart wazuh-agent
```

Real-time monitoring was now active.

---

# Attack Simulation

Modify the monitored file.

```bash
sudo nano /var/www/sensitive/config.php
```

Save the file.

Syscheck immediately detected:

- checksum change
- metadata modification
- content modification

---

Modify permissions.

```bash
sudo chmod 777 /var/www/sensitive/config.php
```

Another alert was generated.

---

# Wazuh Alerts

| Rule | Description |
|-------|-------------|
| 550 | Integrity checksum changed |

The alert included:

- filename
- checksum
- modification time
- permissions
- owner
- previous values
- updated values

---

# MITRE ATT&CK

| Technique | Description |
|------------|-------------|
| T1565.001 | Stored Data Manipulation |

---

# SOC Investigation

The analyst verifies:

- Which file changed?
- Who modified it?
- Was the change authorized?
- Was a privileged account involved?
- Were other alerts generated around the same time?
- Does the modification indicate malware or persistence?

Because the modification was intentionally performed during the laboratory, the activity was considered expected.

---

# Security Impact

File modifications may indicate:

- Malware deployment
- Web shell installation
- Configuration tampering
- Persistence
- Insider activity

Without File Integrity Monitoring, these actions could remain undetected.

---

# Recommendations

- Monitor critical directories.
- Enable real-time monitoring.
- Use report_changes.
- Restrict write permissions.
- Review checksum alerts immediately.
- Correlate file changes with authentication logs.

---

# Scenario 3 — Privilege Escalation Detection

---

# Objective

Validate Wazuh's ability to detect administrative actions performed after obtaining access to a Linux system.

This scenario reproduces a common post-compromise technique in which an attacker creates a new privileged account and performs administrative operations.

---

# Background

After gaining access to a system, attackers rarely stop at a standard user account.

Typical objectives include:

- Creating persistence
- Obtaining administrator privileges
- Executing privileged commands
- Maintaining long-term access
- Disabling security controls

For this reason, monitoring privileged activity is a critical capability for every SOC.

---

# Environment Preparation

The Ubuntu endpoint was already connected to the Wazuh Manager.

The Wazuh Agent was active and forwarding authentication and system events.

---

# Attack Simulation

## Step 1 — Create a New User

```bash
sudo useradd -m soc_test
```

Purpose:

Create a new local account that simulates an attacker establishing persistence.

---

## Step 2 — Grant Administrative Privileges

```bash
sudo usermod -aG sudo soc_test
```

Purpose:

Add the newly created account to the **sudo** group.

This allows the account to execute privileged commands.

---

## Step 3 — Assign a Password

```bash
sudo passwd soc_test
```

During the laboratory, the system displayed the warning:

```text
BAD PASSWORD:
The password is shorter than 8 characters
```

The password was still accepted because this was a controlled laboratory environment.

---

## Step 4 — Authenticate Through SSH

```bash
ssh soc_test@192.168.56.101
```

Authentication generated the following log:

```text
Accepted password for soc_test from 192.168.56.1
```

---

## Step 5 — Execute Privileged Commands

Example:

```bash
sudo whoami
```

Expected output:

```text
root
```

This confirms that the account successfully obtained administrator privileges.

---

# Indicators of Compromise (IOCs)

During the investigation, the analyst observes several indicators:

- New account creation
- Administrative group modification
- Password assignment
- Successful SSH login
- New privileged session
- sudo execution

Individually, these events may be legitimate.

Together, they strongly indicate privilege escalation activity.

---

# SOC Investigation

The SOC analyst investigates several questions:

- Who created the account?
- Why was it created?
- Was the account authorized?
- Was the administrator group modified intentionally?
- Which commands were executed afterward?
- Were files modified?
- Were additional users created?

Correlating these events provides a complete view of the attacker's activity.

---

# Security Impact

Unauthorized administrator creation can allow attackers to:

- Maintain persistence
- Disable security controls
- Install malware
- Access sensitive information
- Move laterally inside the network

---

# Recommendations

- Monitor all account creations.
- Monitor privileged group modifications.
- Review every sudo execution.
- Enable MFA for administrators where possible.
- Audit administrative activity regularly.
- Alert immediately on unexpected privileged accounts.

# SOC Investigation Workflow

A Security Operations Center analyst would typically investigate the attack in the following order:

1. Review authentication failures.
2. Confirm successful authentication.
3. Identify the authenticated account.
4. Verify account privileges.
5. Detect administrative actions.
6. Review file modifications.
7. Correlate all alerts.
8. Determine whether the activity is malicious or authorized.

This methodology reduces false positives while improving detection accuracy.

# Lessons Learned

This laboratory highlighted several key principles of defensive security:

- Effective monitoring begins with proper log collection.
- Authentication events provide valuable indicators of compromise.
- File Integrity Monitoring is essential for detecting unauthorized changes.
- Privilege escalation is one of the most critical stages of an attack.
- Correlating multiple alerts provides significantly more context than investigating isolated events.
- Clear documentation is as important as technical detection.
